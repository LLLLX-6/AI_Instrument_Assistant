# Phase 7B.4: DeepSeek Harness TypeScript Hardware Plugin

Status: **PASS (automated fake-backend scope)**. This phase validates the
TypeScript adapter against the frozen official Harness source and the existing
Python fake HardwareToolRuntime composition. It does not claim real DS1102Z-E
IPC validation, Agent behavior, physical cancellation, artifact retrieval, or
durable request recovery.

## Frozen compatibility baseline

- Official repository: `deepseek-ai/deepseek-harness`
- Git commit: `d347e703908d0406b7a7ef80e3a0e594d86b2215`

- Required Node range: `^22.19.0 || >=24.0.0`
- Compatibility policy: exact-reviewed-shape-only

The checkout is supplied through `DEEPSEEK_HARNESS_DEV_ROOT`. The preparation
script verifies the exact Git commit, package versions, and built library
entrypoints before creating ignored local junctions. No official Harness source
is copied or committed, and no `alpha.2`, release candidate, or floating
dependency is accepted.

## Architecture

```text
official Cordis Context + ToolRuntime
  -> aia-hardware-tools TypeScript plugin
  -> projected static Tool contracts
  -> HarnessHardwareIpcClient
  -> authenticated ws://127.0.0.1:<port>
  -> Python HarnessHardwareServer
  -> HardwareToolRuntime
```

Cordis owns the plugin lifecycle through `ctx.effect()`. The five tools remain
registered while the backend is offline; the effect starts and disposes the IPC
client. The plugin does not start Python, access VISA/SCPI, import a driver,
fetch an artifact, or register a dynamic operation surface.

## Schema projection compatibility

The canonical Hardware Tool Schema remains the source of truth. Generated
TypeScript contracts contain its SHA-256 and are regenerated by the Python
projection pipeline; they are never edited by hand. Unsupported constraints are
listed explicitly as deferred to the Python canonical validator.

The frozen Harness validator accepts a narrower JSON Schema subset than JSON
Schema 2020-12: a node containing only `const` or `enum` must also contain
`type` or `oneOf`. The adapter-boundary projector therefore adds a deterministic
type only when the source omits both:

```text
{ const: "hardware.get_status" }
  -> { const: "hardware.get_status", type: "string" }

{ enum: [1, 2] }
  -> { enum: [1, 2], type: "integer" }
```

Safe scalar inference is limited to string, boolean, integer, and finite number.
Boolean is checked before integer. Empty, mixed, null-containing, object, array,
and non-finite sets fail closed. Existing `type` and `oneOf` are unchanged.
The canonical file is not modified.

## Authentication and transport lifecycle

The client implements `hello -> challenge -> prove -> accepted` using the
independent Harness-Hardware 256-bit PSK and HMAC-SHA256. Each physical attempt
creates a new client nonce and local generation; reconnect requires a new
challenge, proof, session, and socket. TCP/WebSocket open is never treated as
authentication.

The explicit client states are:

```text
DISCONNECTED -> CONNECTING -> AUTHENTICATING -> AUTHENTICATED
       ^              |              |               |
       +-- RETRY_WAIT <- DISCONNECTING <--------------+
                    -> RECONNECT_EXHAUSTED
```

Reconnect delays are bounded at 0.5 s, 1 s, 2 s, and 5 s. Authentication
rejection is not retried automatically. Generation guards prevent late socket
callbacks from changing a newer connection. Heartbeat ping/pong is session
bound and contains no hardware operation.

The secret is loaded from a local file, never from Tool arguments, source,
patch content, or protocol frames. The loaded byte buffer is zeroed after proof
construction or teardown. Secret-load failures are caught immediately and
converted into bounded adapter failures, including during reconnect.

## Request, retry, timeout, and cancellation semantics

Each Tool call receives a unique `message_id` and moves through
`NOT_SENT -> SENT_UNCONFIRMED -> RESPONSE_RECEIVED`. The outer response,
`reply_to`, operation, session, and canonical inner operation must correlate.
Unknown correlation is treated as a protocol failure; duplicate and late
responses are ignored with bounded diagnostics.

An in-flight request is never replayed. Disconnect or request timeout after send
returns `indeterminate_execution / SENT_UNCONFIRMED`. Reconnect is only for
future calls. Abort before send reports `client_cancelled_wait / NOT_SENT`;
abort after send reports that the caller stopped waiting with
`SENT_UNCONFIRMED`. Neither path claims that physical measurement stopped.

Hardware `ok=false` is a valid structured Tool value. Only adapter failures use
Harness execution-failure semantics:

- `ipc_authentication_failed`
- `backend_protocol_mismatch`
- `backend_unreachable`
- `backend_response_invalid`
- `indeterminate_execution`
- `request_timeout`
- `client_cancelled_wait`

Messages are fixed and bounded; stack traces, Python paths, credential details,
VISA resources, and SCPI data are not forwarded.

## Canonical result and artifact semantics

Tool values preserve `contract_version`, `ok`, `operation`, `result/error`,
observations, quality, warnings, coherence, provenance, and artifact metadata.
The bounded renderer presents only a concise summary. `ArtifactReference` stays
opaque: the plugin neither dereferences `memory://` nor returns waveform sample
arrays.

## Validator compatibility adjustment

The TypeScript protocol wrapper keeps Ajv `strict: true` and disables only
`strictTypes`. This is necessary because the reviewed composition schemas use
`unevaluatedProperties` across referenced/all-of object shapes without repeating
a local `type: object`. Validation keywords, formats, references, unknown-keyword
checks, and `additionalProperties` behavior remain enabled; validation semantics
are not relaxed.

## Manual fake smoke test

No oscilloscope is required. Run from the AI Instrument Assistant repository.

Terminal A — initialize the independent secret once, then start the persistent
fake backend:

```powershell
.venv\Scripts\python.exe -m ai_instrument_assistant.integrations.harness_hardware.cli --backend fake --initialize-secret
```

On later runs omit `--initialize-secret`:

```powershell
.venv\Scripts\python.exe -m ai_instrument_assistant.integrations.harness_hardware.cli --backend fake
```

Terminal B — point to the exact official checkout, verify/build the plugin, and
invoke all five tools through the frozen official Context + ToolRuntime:

```powershell
$env:DEEPSEEK_HARNESS_DEV_ROOT = 'C:\path\to\the\frozen\deepseek-harness'
$env:AIA_HARNESS_HARDWARE_ENDPOINT = 'ws://127.0.0.1:49625'
$env:AIA_HARNESS_HARDWARE_SECRET_FILE = (Resolve-Path '.aia-secrets\harness-hardware-psk.txt').Path
npm run build --workspace @aia/deepseek-harness-hardware
npm run smoke:fake --workspace @aia/deepseek-harness-hardware
```

The production plugin gives these process-local environment references
precedence over Cordis configuration. The secret-file reference must be an
absolute path so a Harness launched from another working directory cannot
silently authenticate with an unrelated relative file. No secret-file path is
hard-coded: the committed Cordis patch keeps the established local default,
while production and Web runs must supply `AIA_HARNESS_HARDWARE_SECRET_FILE`
(or explicit runtime configuration) with an absolute resolved path.

### Trust boundaries after reconciliation

- **Operation scopes.** Strict behavior is the default and the only production
  behavior. `TrustedOperationScope` instances are issued exclusively by trusted
  Host composition: the interactive status authority (one exact status request,
  one one-shot scope) and the interactive RE-001D authority (one prepared
  workflow, then exactly four one-shot scopes after confirmation). There is no
  automatic scope provisioning, no broad or wildcard scope, and no budget-10
  fallback. Requests outside a prepared workflow resolve a fail-closed scope.
- **Physical confirmation.** The plugin never synthesizes a
  `ProbeSetupConfirmation` and never defaults `safeLowVoltageConfirmed` to
  true. The RE-001D authority records two channel confirmations only after the
  user's exact workflow-bound confirmation phrase arrives as a current trusted
  user chat event; generic affirmatives ("yes", "confirm") never authorize, and
  any other text revokes the prepared workflow as stale.
- **Egress inspection.** The egress boundary inspects three model-output
  surfaces: final text, tool-call arguments, and reasoning blocks. Final text is
  additionally grounding-checked against trusted evidence; tool arguments are
  the surface that reaches Hardware IPC. Reasoning blocks are model-internal
  intermediate state consumed by neither dispatch nor grounding, so a
  developer-local `AIA_RELAX_EGRESS_REASONING` opt-in may skip only that
  reasoning inspection — never text or tool-argument inspection — and it mints
  no scope, confirmation, or other authority.
- **Hardware IPC authentication.** Raw Hardware IPC proof verification is always
  enabled; there is no relaxed mode that bypasses it. Wrong-PSK connections fail
  closed before any Hardware request.

The smoke output contains only bounded operation, `ok`, and artifact metadata
summaries. To inspect reconnect behavior, stop Terminal A, start the smoke
command in Terminal B, then restart Terminal A within the client's bounded retry
window. The same client must establish a fresh authenticated session; previously
sent measurements must not be replayed. If the retry window expires first, the
smoke command reports a bounded backend-unavailable failure.

The build also creates ignored development-only files:

- `extensions/deepseek-harness/dist/index.js`
- `extensions/deepseek-harness/build/cordis.dev.patch.yml`

The generated development patch contains machine-local paths and must never be
committed. The portable package patch contains no secret value.

## Boundaries and non-claims

- No real DS1102Z-E is connected in Phase 7B.4.
- The plugin does not own the production Python process lifecycle.
- No Agent, planner, teaching policy, MCP, or JLCEDA integration is added.
- Cancellation stops client waiting only.
- `memory://` artifacts are not durable or remotely retrievable here.
- Cross-process request recovery and exactly-once physical execution are not
  claimed.
